Gegenlesen · v1

How the system works

Gegenlesen reviews a git change you start from the CLI. Cheap deterministic rules run first, including an OpenAPI / Swagger break check. Two OpenCode reviewers — the two configured models, always both, driven over HTTP inside Docker — review what is left. A third OpenCode session judges the combined findings and drops anything the evidence does not support.

In one paragraph

An operator runs gegenlesen review in a repo. The CLI packs the change and posts it to the local API. A Vapor service unpacks it safely, figures out the git range, and loads matching handwritten and mined rules. Regex, deny-list, sibling-test, and oasdiff checks run without a model. If there is still new work, the host starts opencode serve twice at the same time — model A and model B, each on its own loopback port — and each writes its own findings file. The host assigns stable IDs (tagged with which reviewer) and checks that each cited snippet is actually on those lines. A judge container then keeps, drops, or downgrades the union of both reviewers. Results stay in SQLite (GRDB + FTS5) and show up in the UI, including what the judge filtered as a false positive.

There is no login. One review runs at a time. The host never calls the model API itself — only the sandboxed OpenCode process does. ACP is not used in v1.

How the host drives OpenCode

Each reviewer or judge invocation is a disposable container running opencode serve --hostname 0.0.0.0 --port 4096. Docker publishes that port to 127.0.0.1 on a random host port. A per-job password is set as OPENCODE_SERVER_PASSWORD. The React app never sees this URL.

A review job, step by step

Every upload becomes one job. The worker walks these stages in order. If an incremental upload has no new hunks, the job succeeds after the deterministic step and never starts Docker.

Two ways to look at a change

Rules, context, architecture, learnings

You configure rules in the web UI (/rules). A rule can be a mechanical check, or just guidance for both models — for example “use the project logger, not print.”

You also write context in /context: architecture notes, “never touch Payments”, which logger to use. Those notes are stored and embedded. After each unpack Gegenlesen chunks the tree, embeds new/changed files, and keeps a living architecture card (drafted by a short miner pass, applied only when you accept it).

At review time the host vector-searches those chunks (plus FTS5 and path globs) and writes a small pack to .gegenlesen/context.md for both reviewers. Vectors live in SQLite, not a hosted vector DB.

After a run, /learnings lists what Gegenlesen wants to remember:

  • Suggested rules (from PRs, 👍/👎, “this should be a rule”, or Learn from this job).
  • Suggested architecture updates (modules, loggers, entrypoints).
  • Suggested context notes (“this change taught us X”).

Accept, edit, or dismiss. Nothing auto-applies.

  • Regex, deny-list, sibling-test, and OpenAPI break checks become findings immediately and skip the judge.
  • The reviewers may only write their slot findings files. They cannot edit source or launch subagents.
  • The host drops a finding if the cited snippet is not on those lines. Otherwise the judge’s default is keep.
  • If the judge container dies, the job still succeeds; those verdicts are unavailable.

What v1 is not

No accounts, no GitHub App, no merge gate, no auto-fix, no ACP. The browser does not start reviews — that is gegenlesen review. The SPA is rules, context, learnings, and reading jobs. One machine, Docker, Vapor on 127.0.0.1:8080, OpenCode on loopback-mapped ports.
